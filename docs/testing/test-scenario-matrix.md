# Test Scenario Matrix — Order Management & Order Lifecycle Module

**Purpose:** enumerate every testable behavior for the 3 migrated endpoints, precise enough for a later test-writing phase to implement directly without re-deriving behavior from source. This document contains **no test code and no production-code changes**.

**Endpoints covered** (real paths, per `docs/testing/qa-readiness-notes.md` §1 — note `GET /api/order` has no `/my/` segment despite how it's sometimes referred to informally):
1. `GET /api/order`
2. `GET /api/my/restaurant/order`
3. `PATCH /api/my/restaurant/order/:orderId/status`

**Sourcing rule:** every "Expected Result" is derived from the actual Node/FastAPI source or a named Phase 1–3 document. Anything not directly traceable is marked **[NEEDS VERIFICATION]** in the Evidence Required column rather than asserted as fact.

**Column legend:**
- **Test Type:** `Unit` (service method, mocked repositories, no DB/network) · `Integration` (FastAPI `TestClient` + `get_current_user_id` dependency override) · `Repository` (already covered by `tests/test_repositories.py`, listed for cross-reference only) · `Manual` (requires running the Node server side-by-side) · `Blocked` (not executable until RFOMS-7 auth is implemented)
- **Priority:** `Critical` / `High` / `Medium` / `Low` (same vocabulary as `docs/security-review.md`)

## 3. `PATCH /api/my/restaurant/order/:orderId/status`

Source: `MyRestaurantController.updateOrderStatus` (Node) / `RestaurantService.update_order_status` (`app/services/restaurant_service.py`).

|---|---|---|---|---|---|---|---|

| RST-ORD-PATCH-02 | Restaurant / `update_order_status` | Happy path — full forward lifecycle sequence | Order starts at `placed`; sequential PATCH calls: `paid`→`inProgress`→`outForDelivery`→`delivered` | Unit | Each call returns 200 with the requested status; no call is rejected | High | pytest: 4 sequential calls, each asserted 200 + correct `status` |

## Summary

- **34 scenarios** across the 3 in-scope endpoints, covering every requested category: happy paths, authentication failures, authorization failures, invalid identifiers, nonexistent records, invalid request data, invalid status values, valid lifecycle transitions, the deliberately-omitted "invalid transition rejected" case (replaced with a "not enforced, confirmed accepted" case per the conditional instruction), database persistence, response/status-code validation, error handling, regression cases, and Node/FastAPI parity cases.
- **7 scenarios are `Blocked`** (auth-related, pending RFOMS-7) and **5 are marked `[NEEDS VERIFICATION]`** (require either a live Node server for comparison or deliberate fault injection) — both categories are explicitly called out rather than silently assumed passing.
- **Highest-priority single scenario:** `RST-ORD-PATCH-07` — the ownership-check Node/FastAPI parity deviation (C2). This is the one place FastAPI's behavior is deliberately and correctly different from Node's actual production behavior, and it should be the first scenario implemented as an executable test.
- No test code or production code was written to produce this matrix.
